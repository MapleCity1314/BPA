# 抖店库存浏览器工作流稳定性复盘 v0.1

> 文档类别：工程复盘与问题登记。
>
> 记录时间：2026-08-04
> 记录范围：抖店库存采集工作流从自动调度、浏览器绑定、商品逐项采集、快照持久化到风险评估的完整链路。
> 状态说明：本文保留 2026-08-04 的问题基线；文末追加 2026-08-05 V2 生产验收结果。

## 1. 结论

目前 BPA 库存工作流的基础执行框架已经具备较完整的安全边界：定时调度、进程内防重叠、PostgreSQL 租约、fencing token、逐商品持久化和部分结果恢复均已存在。

但当前只能确认“调度器能够自动触发”，不能确认“浏览器采集能够稳定产出”。真实运行的主要不确定性集中在浏览器会话、外部 RPA 干预、页面瞬时状态、长批次失败语义和诊断证据不足。继续增加整轮重试不能从根本上解决这些问题，反而会延长失败时间并增加标签页、会话和页面状态冲突。

下一阶段应把目标从“让当前脚本多跑几次”调整为：

1. 让浏览器资源具有可验证的独占所有权。
2. 让每个商品成为可隔离、可恢复、可诊断的执行单元。
3. 让解析逻辑能够脱离真实浏览器进行录制夹具回放。
4. 让每一轮都产生明确的成功、部分成功或阻断摘要。
5. 用金丝雀和量化门槛决定是否进入全量扫描及多店铺发布。

- 一次降级运行在浏览器工作流没有正常终态的情况下，恢复了 74 个已经持久化的新鲜商品快照并继续风险评估。
- 高频错误包括：
  - `INVENTORY_SNAPSHOT_OUTPUT_EMPTY`

这些运行数据只能证明定时触发和部分恢复有效，不能证明端到端采集稳定。

## 3. 稳定性的分层定义

“工作流稳定”不能只通过进程是否在线判断，应拆成五层：

| 层级 | 含义 | 当前判断 |
| --- | --- | --- |
| L1 进程稳定 | Core、服务和调度器可以自动启动、异常退出后恢复 | 基础具备 |
| L2 触发稳定 | 每 30 分钟产生一次明确调度记录，不重叠、不重复 | 基础具备，仍需处理僵尸运行 |
| L3 浏览器稳定 | 能锁定正确店铺和页面，不受其他 RPA、弹窗和标签页干扰 | 未达到 |
| L4 数据稳定 | 商品、SKU、渠道库存按门槛完整采集并及时入库 | 未达到 |
| L5 结果稳定 | 预测和风险能够持续使用新鲜、完整、可追溯的数据 | 未达到 |

因此当前结论是：**触发机制基本可用，完整工作流尚未稳定。**

## 4. 当前执行链路

```text
launchd 守护调度器
→ 启动即运行 / 每 30 分钟运行
→ 进程内 running 防重叠
→ 获取 PostgreSQL 店铺租约和 fencing token
→ 刷新订单需求
→ 冻结抖店浏览器资源绑定
→ 校验店铺身份
→ 收集全部在售商品范围
→ foreach 逐商品打开库存抽屉
→ 读取 SKU、占用、未占用和渠道库存
→ 每个商品立即持久化
→ 对新鲜快照执行预测和风险评估
→ 写入调度终态并释放租约
```

该链路的数据库和确定性计算部分相对清晰，主要脆弱点集中在“冻结浏览器资源绑定”到“商品抽屉关闭”之间。

## 5. 根因复盘

### 5.1 工作流批次语义与真实页面可靠性不匹配

库存工作流最多遍历 500 个商品，但当前使用 `onItemError: stop`。在长批次中，即使单商品失败概率很低，任意一次抽屉、浮层或页面瞬时异常都会让整轮无法获得正常终态。

逐商品立即持久化降低了数据丢失范围，但没有解决工作流结果语义：调用方仍可能只看到整轮失败或空输出，而不知道已经保存多少商品、哪些商品失败、是否允许继续建模。

### 5.2 浏览器资源绑定不等于浏览器独占控制

BPA 可以绑定到一个浏览器实例或页面，但其他 RPA 和人工操作并不遵守 BPA 的租约。外部程序仍可切换标签页、改变滚动位置、打开弹窗或抽屉、切换店铺以及抢占焦点。

数据库工作流租约只能防止两个 BPA 调度器同时执行，无法防止另一个 RPA 同时操作同一浏览器窗口。

### 5.3 单商品节点承担过多易变状态

当前库存快照节点同时处理：

- 商品跨页定位和列表滚动。
- 库存编辑入口识别。
- 抽屉打开和就绪判断。
- SKU 表格及商家编码解析。
- 占用库存悬停。
- 渠道浮层识别、虚拟滚动和复位。
- 库存合计校验。
- 抽屉关闭和关闭确认。

这些状态由同一长函数串联，失败后不容易确定是交互问题、页面就绪问题、解析问题还是结构变化。

### 5.4 真实浏览器承担了过多开发反馈

当前开发和调试仍高度依赖真实登录页面。每次修改都可能需要：

- 更新 Adapter 实现和摘要。
- 更新 Extension 能力声明。
- 构建并重新加载扩展。
- 绑定正确浏览器和店铺。
- 人工恢复页面到特定状态。
- 再次执行整条工作流。

缺少系统化的页面录制夹具和离线交互状态回放，使得本可在秒级完成的解析回归需要通过分钟级真实浏览器运行验证。

### 5.5 失败证据没有形成标准诊断包

错误码能够说明阻断类型，但不足以复现现场。当前缺少统一的失败产物，无法稳定回答：

- 失败时 URL 和店铺身份是什么。
- 当前处理到哪个商品、哪一页、哪一个 SKU。
- 抽屉和渠道浮层是否存在、是否可见。
- 当前滚动位置和 DOM 稳定签名是什么。
- 最近完成了哪些受控动作。
- 是否有其他标签页或 RPA 同时改变页面。

因此多个根因可能最终表现为同一个 `INVENTORY_SNAPSHOT_OUTPUT_EMPTY`。

### 5.6 运行状态和真实业务结果存在不一致窗口

已经出现数据库运行记录长期停留在 `running` 的情况。租约过期能够允许下一轮继续，但展示、诊断和运行统计仍会保留错误状态，影响运营判断和稳定性度量。

### 5.7 多店铺能力存在“代码支持”和“部署启用”的差距

当前代码已经支持 `BPA_INVENTORY_SHOPS_JSON` 和浏览器实例唯一性检查，但生产检查时仍使用单店铺兼容变量。多店铺配置能力存在，不代表所有店铺已经被调度、绑定和验收。

## 7. 已有保护与适用边界

以下能力已经存在或正在当前工作树中实现，不应重复建设，但需要完成测试和生产验证：

### 7.1 已有基础保护

- 调度器由 `launchd` 守护并按周期运行。
- 进程内 `running` 标记阻止本进程重叠运行。
- PostgreSQL 租约和 fencing token 防止重复写入和失效持有者继续执行。
- 商品读取后立即持久化，降低长任务失败导致的整批丢失。
- 采集失败但存在新鲜持久化快照时，调度器可以对已保存子集继续风险评估。
- 店铺身份不匹配、登录失效、验证码和未知风险信号保持阻断。

### 7.2 当前工作树中出现、尚需验证的改进

- 渠道浮层支持滚动收集并在结束后复位到顶部。
- 商品不在当前页时支持分页和页面滚动定位。
- 已知“属性自动优化”营销弹窗使用严格白名单关闭，未知弹窗继续阻断。
- 标签页生命周期只跟踪能够归因于当前 BPA 命令的派生标签页。
- 多店铺配置支持浏览器实例唯一性和缺失绑定校验。
- Core 提供按 Browser Instance 隔离的控制租约、续约、释放和 fencing token。
- 生产周期在全量扫描前执行店铺、页面角色、关键表头、未知弹窗和结构摘要金丝雀。
- 金丝雀和组件失败写入固定目录的脱敏诊断 JSON；不保存订单明细和页面全文。

这些改动目前位于未提交工作树中。是否已构建、部署并通过真实页面回归需要单独确认，本文不将其标记为生产已交付。

## 8. 建议的目标执行模型

```text
周期触发
→ 获取店铺和浏览器控制租约
→ 会话、登录、店铺、页面金丝雀
→ 冻结商品范围和数据版本
→ 逐商品状态机
    → 定位商品
    → 打开抽屉
    → 观察并解析 SKU
    → 读取并复位渠道浮层
    → 持久化商品快照
    → 关闭抽屉并恢复页面
    → 单商品失败时保存证据并隔离
→ 生成完整/部分/阻断采集摘要
→ 只对新鲜且合格的已持久化快照建模
→ 关闭命令创建的派生标签页
→ 释放浏览器和工作流租约
```

### 8.1 建议的批次结果

每一轮无论如何结束，都应返回固定结构：

```ts
interface InventoryCollectionSummary {
  readonly discovered: number;
  readonly attempted: number;
  readonly persisted: number;
  readonly failed: number;
  readonly skipped: number;
  readonly coverage: number;
  readonly outcome: "complete" | "partial" | "blocked";
  readonly failedProducts: readonly {
    productId: string;
    stage: string;
    errorCode: string;
    evidenceId: string;
  }[];
}
```

调用方应根据 `outcome` 和 `coverage` 判断是否继续风险评估，不应仅根据工作流是否到达 `succeeded` 终态判断数据是否存在。

### 8.2 建议的单商品状态

```text
located
→ drawer_opening
→ drawer_ready
→ sku_table_observed
→ channel_overlay_observed
→ snapshot_validated
→ persisted
→ drawer_closed
→ page_restored
```

每个状态都应有明确的就绪条件、超时、错误码和证据。只读节点可以进行有限的局部恢复，但不能无界重试，也不能绕过登录、验证码、店铺不匹配或未知弹窗。

## 9. 快速编写和发布路径

新的浏览器工作流应采用固定的“录制、回放、探针、灰度”流程：

1. 在真实页面只读录制正常状态和已知异常状态。
2. 将 DOM、结构摘要和截图脱敏后保存为版本化夹具。
3. 先编写纯观察和解析函数，使用夹具完成大部分调试。
4. 通过脚手架一次生成 Node、Adapter capability、Handler、测试和摘要更新位置。
5. 在真实浏览器只运行一个固定商品探针。
6. 扩大到 5 个覆盖不同 SKU 和渠道数量的商品。
7. 单店全量运行并观察至少连续多个周期。
8. 按店铺逐一绑定和灰度，禁止一次性开启所有店铺。
9. 任何新页面形态或生产故障都必须先沉淀为回归夹具，再发布修复。

## 10. 建议稳定性门槛

| 指标 | 建议门槛 |
| --- | ---: |
| 调度记录产生率 | 不低于 99% |
| 浏览器控制租约冲突可解释率 | 100% |
| 执行前金丝雀通过率 | 不低于 98% |
| 单商品采集成功率 | 不低于 99% |
| 单轮商品覆盖率 | 不低于 98% |
| 2 小时内库存快照新鲜率 | 不低于 95% |
| 无人工干预完整运行率 | 不低于 95% |
| 僵尸 `running` 记录 | 0 |
| 重复开放事件 | 0 |
| 无证据的结构错误 | 0 |

只有 L1 至 L5 指标分别达标，才能把工作流标记为生产稳定。单次成功或调度器进程在线不能作为上线依据。

## 11. 建议实施顺序

### P0：先恢复可诊断、可持续运行

1. 将单商品错误从整轮停止改为隔离并继续，同时保留失败率熔断。
2. 固化批次结果结构，消除“已入库但输出为空”的歧义。
3. 增加浏览器控制租约，协调 BPA 与其他 RPA。
4. 增加执行前金丝雀。
5. 自动回收无有效租约的僵尸运行记录。
6. 为结构和交互失败保存脱敏诊断包。

### P1：降低后续工作流开发成本

1. 建立抖店库存页面录制夹具库。
2. 将单商品节点重构为可观测状态机，并分离交互和纯解析。
3. 提供浏览器 Node 脚手架和单节点 smoke runner。
4. 完成标签页创建、归属、恢复和释放闭环验收。
5. 把 L1 至 L5 指标加入运行面板。

### P2：完成多店铺生产推广

1. 每个店铺配置唯一浏览器资源。
2. 按店铺记录金丝雀、全量覆盖率和最近成功时间。
3. 单店达标后再开放下一店，保留快速停用开关。
4. 完成连续运行、浏览器掉线、弹窗、Core 重启和数据库短暂不可用演练。

## 12. 待确认事项

1. 当前工作树中的渠道滚动、分页定位、弹窗白名单和标签页生命周期改动是否已经构建并部署到 Mac mini。
2. 其他 RPA 是否能够接入统一的浏览器控制租约；若不能，需要确定物理隔离浏览器 Profile 的方案。
3. 商品级允许失败比例和全轮熔断门槛应根据真实商品数与运营容忍度确定。
4. 诊断包的保存期限、脱敏规则和磁盘配额尚未确定。
5. 多店铺各自的固定浏览器实例、登录维护责任人和异常响应机制尚未形成正式清单。

## 13. 本轮决策建议

- 不把“调度器在线”描述为“工作流稳定”。
- 不通过无界整轮重试掩盖页面和会话问题。
- 不允许两个 RPA 同时控制同一个店铺浏览器资源。
- 不因单商品可恢复错误丢弃已经验证并持久化的商品快照。
- 不对未知弹窗、验证码、店铺不匹配和风险信号进行自动绕过。
- 后续浏览器工作流必须优先具备离线夹具回放能力和失败证据产物。
