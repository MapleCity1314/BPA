## 2. 已确认事实

1. PostgreSQL 能产生库存快照、预测和风险事实；页面长期显示订单读取不等于数据库没有处理数据。
2. 多店铺恢复脚本对每店无条件读取近期订单，失败时重复执行，没有先根据新鲜度跳过。
3. 高频错误集中在 `BROWSER_AUTH_REQUIRED`、`INVENTORY_SHOP_SWITCH_ENTRY_NOT_READY` 和 `INVENTORY_PRODUCT_PAGE_NOT_READY`。
4. 部分 `BROWSER_AUTH_REQUIRED` 是页面已切换但 Extension 尚未稳定发布店铺观察的瞬时误分类，不一定是真实登录失效。
5. 其他 RPA 和人工操作可以改变标签页、滚动、弹窗和店铺；PostgreSQL 租约不能阻止外部控制者。
6. launchd 退出码、应用状态 JSON 和数据库运行终态可能不一致，单独使用任一信号都可能重复触发或错误报喜。
7. 渠道冷启动 `unknown` 可能向上污染商品级风险，数据不足与确定性库存风险尚未完全分开。

## 3. 分层判断

| 层级 | 当前判断 | 说明 |
| --- | --- | --- |
| PostgreSQL 事实持久化 | 基本可用 | 已有库存、预测和风险事实 |
| 纯计算节点 | 基本可用 | 不是当前主要失败来源 |
| BPA Core | 未发现整体失效 | 能执行已发布工作流 |
| 抖店 Browser Adapter | 主要不稳定点 | 绑定、就绪、切店和错误分类脆弱 |
| 多店铺 App 编排 | 需要解耦 | 订单、库存和计算串行且存在整段重试 |
| 共享 RPA 环境 | 重要外部风险 | 缺少统一控制租约或物理隔离 |

当前问题应描述为浏览器运行时、Adapter 就绪语义和 App 编排尚未达到稳定生产要求，而不是“BPA 整体不可用”。

## 4. 已接受决策

### D-01：生产只有一个调度控制面

App 调度器和 launchd 负责确定性执行。Codex 只监督、解释，并在无进程、无有效租约且数据确实过期时安全触发唯一入口。

### D-02：Codex 只指向新多店铺入口

Codex 自动任务仅允许检查和安全触发 `com.bpa.inventory-multishop-recovery`。两个旧入口不再启动，Codex 不直接调用内部刷新脚本。

### D-03：订单、库存和计算独立刷新

- 库存采集只发布库存事实。
- 近期订单按店铺新鲜度独立刷新，120 分钟内复用。
- 历史订单独立同步，完整日门槛为 36 小时。
- 预测和风险消费固定事实版本，可独立补算。

### D-04：运行状态使用组合事实

进程、有效 PostgreSQL 租约和数据库运行记录共同决定是否在运行。状态文件和前端属于派生视图，不一致时报告故障但不立即重触发。

### D-05：部分成功是一等结果

每轮返回 `complete`、`partial`、`blocked` 或 `degraded`，并报告发现、尝试、持久化、失败和跳过数量。已经入库的数据不得显示为无数据。

### D-06：浏览器控制权独立建模

Page Binding 说明使用哪个页面，不代表独占控制。应增加浏览器 Control Lease；外部 RPA 无法接入时使用独立 Profile、窗口或实例隔离。

### D-07：数据质量与业务风险分流

渠道冷启动、映射不足和覆盖不足形成数据质量状态，不再自动污染商品级确定性库存风险。

### D-08：AI 不成为生产依赖

BPA Core、App Scheduler 和已发布 Workflow 在没有 AI 时持续执行。AI 用于设计、开发、诊断和解释，不承担固定周期、租约、幂等和事实处理。

## 5. 完成状态

### 已完成

- Codex 自动任务改为监督并安全触发新多店铺入口。
- 自动任务停止引用旧任务，使用 120 分钟库存和近期订单有效期。
- 自动任务不再直接调用内部刷新脚本。
- 自动任务增加状态不一致、部分成功和浏览器控制冲突判断。

### 尚未完成

- 渠道冷启动满 3 天后的覆盖率与一致性验收。
- 部分店铺 P90 覆盖率校准到 85%–95% 放行区间。
- Domain Event、External Event Trigger 和可视化运行日历。

### 2026-08-05 已交付补充

- 近期订单按 120 分钟新鲜度跳过，订单失败不再阻断库存采集。
- 生产周期按 `canary`、`orders`、`inventory`、`risk` 独立记录组件终态。
- Core Browser Control Lease、Extension 稳定金丝雀和专用 Chrome 实例已接入生产周期。
- 统一批次摘要、逐商品持久化、局部恢复与脱敏诊断目录已经上线。
- 渠道冷启动不再生成开放库存风险，面板将其作为数据质量状态处理。
- Manual、Schedule、Dataset TriggerSpec 的 Schema、SQLite、Core API、CLI 和运行时已实现。
- 首轮 13 店生产验收完成：319 / 319 个商品持久化，13 个风险组件全部成功。
- 第二轮由 launchd 无人值守触发并完成，13 店库存覆盖率 100%，证明生产不依赖
  Codex 人工调用。
- 榆园儿订单失败已定位为 `RECENT_ORDER_RESULT_LIMIT_EXCEEDED`，不是登录失败；
  浏览器订单超过 500 条时由 WDT 热数据镜像接管，实测同步 939 条增量事实。
- WDT 补偿后完成同店新库存快照和风险重算，面板恢复确定性判断并展示 3 个严重
  SKU 风险；订单数据质量提醒归零。

## 6. 不再采用的做法

- 不让 Codex 成为主调度器。
- 不在每店每轮无条件读取订单。
- 不通过整轮重试掩盖页面未就绪。
- 不用数据库租约冒充浏览器独占。
- 不将调度器在线描述为端到端业务稳定。
- 不将渠道 `unknown` 冒充确定性缺货风险。

## 7. 验收重点

- 近期订单有效时，库存周期不重复读取订单。
- 停止 Codex 后，App 仍能按计划产生运行记录。
- 页面刷新或 Extension 短暂重连不会立刻误判为登录失效。
- 每轮可以解释成功、失败、跳过商品和是否继续建模。
- 其他 RPA 持有控制权时，BPA 明确等待、跳过或停止。
- 面板分别展示业务风险、数据质量、采集故障和调度故障。
