> 记录时间：2026-07-27

> 项目位置：`/Users/yibazhua/Documents/重点项检查插件`

## 1. 本轮结论

“抖店重点项检查器”不是一个等待验证的概念原型，而是 BPA 已经解决真实问题的第一个业务场景。

它已经形成了完整的执行闭环：

```text
选择任务范围
→ 完整采集商品
→ 主数据匹配和规则推断
→ 人工确认预检
→ 顺序检查商品
→ 临时操作和补偿还原
→ 保存问题与审计
→ 异常处理
→ 人工复核式填空
```

但这些能力目前主要以专用代码形式固化在浏览器扩展中，还没有被提炼为可声明、可组合、可复用的 BPA Workflow 和 Node。

因此，下一阶段不应推翻或重写这个插件，而应把它作为：

- BPA 的第一个参考实现。
- BPA Workflow 语义的事实来源。
- 第一批通用节点和抖店自定义节点的提取对象。
- Workflow Engine 的行为基准。
- 后续重构过程中的回归测试基准。

## 2. 项目当前形态

### 2.1 产品目标

插件批量检查抖店商品编辑页中的：

- 普通必填空值。
- 选择包装后动态出现的食品安全字段。
- 抖店“填写检查”产生的平台提醒。
- 可基于已确认主数据安全填写的空白文本字段。

### 2.2 技术栈

- TypeScript
- WXT
- Chrome/Edge Manifest V3
- React
- Ant Design
- Dexie / IndexedDB
- Zod
- Vitest
- Playwright

## 3. 已经存在的 BPA 特征

### 3.1 确定性 Workflow

项目已经拥有明确的执行顺序和状态：

```text
queued
→ preparing
→ collecting
→ awaiting_preflight
→ checking
→ completed
```

同时支持：

- `paused_auth`
- `paused_manual`
- `interrupted`
- `cancelled`
- `failed`

这已经是一个专用 Workflow Engine，只是 Workflow 仍然写死在代码中。

### 3.2 人工治理点

已经存在明确的人工参与边界：

- 包装预检必须确认。
- 验证码和登录问题交给人。
- 自动切店失败后暂停。
- 商品范围不完整时禁止继续。
- 连续页面结构异常时熔断。
- 自动填写完成后由人检查和保存。

### 3.3 动作后验证

项目没有把“动作调用成功”当作业务成功：

- 切店后再次核对店铺身份和列表稳定性。
- 列表采集后核对采集数量与页面总数。
- 选择包装后等待动态字段稳定。
- 检查完成后验证包装是否还原。
- 填写字段后重新读取页面值。

### 3.4 补偿操作

“临时选择包装 → 检查动态字段 → 还原原值”是一个完整的补偿事务。

它说明 BPA 节点不能只提供 `click` 和 `select`，还需要表达：

- 动作前快照。
- 主动作。
- 后置检查。
- 补偿动作。
- 补偿验证。
- 补偿失败后的熔断策略。

### 3.5 可恢复执行

当前项目能够：

- 恢复后台中断时仍在运行的队列项。
- 回收失联标签页。
- 将执行中的商品恢复为待检查。
- 对单商品进行有限重试。
- 在浏览器重启后将任务标记为等待人工恢复。

### 3.6 安全能力声明

现有代码已经显式声明：

```text
autoFill = true
packagingPreview = true
reviewFillOnly = true
autoSave = false
autoPublish = false
```

这可以演化为 BPA 的节点级 Capability 与 Permission 模型。

## 5. 为什么需要 `node_gen`

通用 BPA 至少需要两个相互独立的生成系统：

```text
workflow_gen
    │
    │ 只使用 Node Catalog 中已发布的节点
    │
    ├── 能力足够 ──→ 生成 Workflow
    │
    └── 能力不足 ──→ 生成 Node Requirement
                           │
                           ▼
                       node_gen
                           │
                           ▼
                   节点实现、测试和审核
                           │
                           ▼
                     Node Catalog
                           │
                           └──→ workflow_gen 重新生成
```

`workflow_gen` 不应该在发现能力缺口时直接生成并执行临时代码。否则 Workflow 的确定性、安全审查和公司资产边界都会失效。

`node_gen` 的职责是把一个经过描述的能力缺口转化成候选节点包，但候选节点在通过测试和审核前不能进入正式 Workflow。

## 6. `workflow_gen` 与 `node_gen` 的职责

### 6.1 `workflow_gen`

负责：

- 理解业务目标。
- 确定 Workflow 输入、输出和验收标准。
- 从 Node Catalog 查询已有节点。
- 组合控制流和数据流。
- 配置重试、补偿、权限和人工确认。
- 生成 Workflow 测试。
- 静态校验和模拟。
- 发现节点能力缺口。

不负责：

- 生成任意浏览器代码。
- 绕过未满足的节点依赖。
- 自动发布新节点。
- 在任务运行时修改节点实现。

### 6.2 `node_gen`

负责：

- 将能力缺口整理为 Node Requirement。
- 判断应该创建组合节点、服务节点还是浏览器适配节点。
- 优先使用已有低层节点组合。
- 生成节点定义、实现骨架、测试、权限和风险说明。
- 运行节点契约测试和平台夹具测试。
- 生成版本差异和审核材料。

不负责：

- 未经审批直接注册正式节点。
- 在浏览器中执行生成阶段的任意代码。
- 让节点获得未声明的权限。
- 用一个平台节点伪装成通用节点。
- 在节点内部隐藏完整业务 Workflow。

## 7. `node_gen` 应生成什么

一个完整候选节点包至少包含：

```text
nodes/doudian/product-collect/
├── node.yaml
├── README.md
├── src/
│   └── execute.ts
├── tests/
│   ├── contract.test.ts
│   ├── fixtures.test.ts
│   └── safety.test.ts
├── fixtures/
│   ├── normal.html
│   ├── virtual-list.html
│   └── auth-challenge.html
├── permissions.yaml
├── changelog.md
└── generation-report.json
```

### 7.1 `node.yaml`

描述：

- 节点 ID 和版本。
- 运行环境。
- 输入、输出和配置 Schema。
- 权限和风险等级。
- 超时、重试和幂等语义。
- 可能返回的错误码。
- 要求保存的证据。
- 支持的平台适配器版本。

示例：

```yaml
apiVersion: bpa/v1alpha1
kind: NodeDefinition

metadata:
  id: doudian.product.collect
  version: 1.0.0
  title: 完整采集抖店商品列表

spec:
  runtime: browser
  adapter: doudian

  inputSchema:
    type: object
    required: [shopKey]
    properties:
      shopKey:
        type: string

  outputSchema:
    type: object
    required: [products, expectedCount, complete, scopeSignature]
    properties:
      products:
        type: array
      expectedCount:
        type: integer
      complete:
        type: boolean
      scopeSignature:
        type: string

  permissions:
    - browser.dom.read
    - browser.dom.scroll
    - browser.dom.click.pagination

  risk:
    level: low
    mutatesBusinessData: false

  execution:
    timeout: 240s
    idempotency: repeatable_read
    maxAttempts: 3

  evidence:
    required:
      - observedShop
      - expectedCount
      - collectedCount
      - scopeSignature
```

### 7.2 测试

`node_gen` 不能只生成正向测试。至少需要：

- 正常页面。
- 页面为空。
- 虚拟列表。
- 多页数据。
- 动态新增商品。
- 店铺发生变化。
- 筛选范围发生变化。
- 登录或验证码。
- DOM 锚点缺失。
- 超时和扩展断线。
- 权限拒绝。

### 7.3 生成报告

`generation-report.json` 应记录：

- 需求来源。
- 参考了哪些已有代码或页面证据。
- 复用了哪些节点。
- 新增了哪些权限。
- 哪些逻辑是事实。
- 哪些逻辑是 Codex 推断。
- 尚未覆盖的页面变体。
- 建议审核人。

## 8. 节点类型

### 8.1 组合节点

只组合已发布节点，不引入新执行代码。

优先级最高、风险最低，也是 `node_gen` 首先应该尝试的形式。

### 8.2 Engine 节点

运行在 BPA Worker 中，用于：

- 规则计算。
- 数据转换。
- 文件处理。
- 内部 API 调用。

它默认没有浏览器权限。

### 8.3 Browser Adapter 节点

运行在浏览器扩展中，用于平台专有 DOM 能力。

它必须：

- 随扩展构建和正式版本发布。
- 使用白名单动作。
- 声明允许访问的域名。
- 不接受远程动态代码。
- 具备页面夹具测试。

### 8.4 Human 节点

用于审批、补充信息和人工接管。它不需要由 `node_gen` 频繁生成，第一阶段应由 BPA Core 提供稳定的通用实现。

## 9. Node Catalog

Node Catalog 不能只是一张节点名称列表。每个版本需要保存：

- Node Definition。
- 实现包摘要。
- 发布状态。
- 运行环境。
- 权限。
- 风险等级。
- 输入输出 Schema。
- 依赖节点。
- 支持的平台与适配器版本。
- 测试结果。
- 审核记录。
- 废弃和迁移信息。

建议状态：

```text
requirement
→ draft
→ generated
→ validated
→ tested
→ approved
→ published
→ deprecated
```

Workflow 只能引用 `published` 节点的固定版本。

## 11. 从重点项插件开始的提取顺序

### 第一阶段：建立行为基准

- 固定当前插件版本。
- 保留现有单元测试和端到端测试。
- 保存典型页面夹具和任务结果。
- 明确现有场景的业务验收标准。

### 第二阶段：提取 Schema

- Node Definition Schema。
- Workflow Schema。
- 统一错误码。
- 统一执行结果。
- Evidence Schema。
- Permission Schema。

### 第三阶段：先提取无平台依赖节点

- `control.retry`
- `control.circuit_breaker`
- `control.compensate`
- `human.approve`
- `human.takeover`
- `evidence.persist`

### 第四阶段：提取抖店节点

- 列表采集。
- 切店。
- 页面就绪。
- 必填检查。
- 包装预览。
- 复核填写。

### 第五阶段：把当前硬编码编排表达为 Workflow

此时 Workflow 只替代调度和组合层，原有经过验证的页面适配逻辑继续作为节点实现使用。

### 第六阶段：接入生成器

先实现：

- Node Catalog 查询。
- `workflow_gen` 草稿生成和校验。
- `node_gen` 组合节点生成。

浏览器代码节点的自动生成应最后开放，并且只能生成候选代码，不能直接发布或热加载。

## 12. 当前风险

### 12.1 过早追求通用

如果没有以重点项插件的真实行为为基准，容易设计出形式完整但无法处理虚拟列表、慢加载、动态字段和补偿失败的抽象。

### 12.2 节点颗粒度错误

- 过细：Workflow 退化为大量点击和选择器，类似传统 RPA。
- 过粗：一个节点隐藏完整业务流程，无法组合、验证和治理。

建议的节点颗粒度是“稳定、可验证的业务或页面能力”。

### 12.3 `node_gen` 成为任意代码入口

必须坚持：

- 生成与执行分离。
- 候选与发布分离。
- Workflow 与节点实现分离。
- 浏览器节点与服务端节点分离。
- AI 建议与人类授权分离。

## 13. 下一轮建议产出

下一轮优先完成以下四份机器可读定义：

1. `node-definition.schema.json`
2. `workflow.schema.json`
3. `execution-event.schema.json`
4. `permission.schema.json`

然后从重点项插件中选取两个节点制作样例：

- 一个通用节点：`control.compensate`
- 一个平台节点：`doudian.product.collect`

这样可以同时验证通用控制能力和真实浏览器能力，避免只设计纸面 Schema。
