# BPA 产品形态定义 v1

> 文档类别：产品形态与边界的正式约定。
> 记录时间：2026-08-06。
> 权威等级：normative。本文件定义"BPA 是什么、不是什么"，
> 以及公司业务与产品之间不可越过的分层边界。
> 与本文件冲突的计划文档一律以本文件为准。

## 0. 一句话形态

**BPA 是一台公司自动化服务器：一台机器托管所有重复网页流程，定时跑、无人值守、
每一步留证据、出错自动停、不确定的写操作绝不重试。**

这句话是对外说明、功能取舍和路线排序的唯一判据。任何一个需求如果不能被这句话
解释，它就不属于当前产品。

## 1. 形态决定：自动化服务器，不是桌面工具

### 1.1 事实前提

- 所有工作流当前部署在一台 Mac mini 上，该机器是公司 server。
- 库存浏览器当前由 launchd `KeepAlive` 常驻并复用固定 profile；产品目标仍是按需执行，
  是否以及如何收敛必须先由阶段 0 的资源曲线和登录稳定性证明。
- 目前只有一名使用者，且每个应用对应一个独立控制台。
- 登录态目前依赖人工接收验证码。
- 触发监控目前由 AI 承担（这是必须收敛的技术债，见 §7）。

### 1.2 由此确定的形态

BPA 不是"装在每个员工电脑上的自动化工具"。它是**一台常驻服务器 + 远程 Web 控制台**：

```text
┌──────────────── 自动化服务器（一台机器）─────────────────┐
│  BPA Core（常驻服务）                                     │
│    ├─ Registry / Runs / Events / Evidence（SQLite）       │
│    ├─ Engine（编译后固定 IR 执行）                        │
│    ├─ Trigger（固定规则，定时/数据/事件）                  │
│    └─ Browser Gateway                                     │
│           │ Native Messaging                              │
│  浏览器执行端（按需启动，持有真实登录态）                   │
│    └─ Extension（固定动作集，受签名授权约束）              │
└───────────────────────────────────────────────────────────┘
                    │ HTTP（局域网 / 内网）
                    ▼
        远程 Web 控制台（客户 90% 时间待在这里）
        流程列表 · 定时配置 · 运行记录 · 结果 · 证据 · 失败告警
```

**客户端零安装。** 使用者用浏览器打开控制台即可，不需要在自己机器上装任何东西。
需要安装的只有那台服务器。

### 1.3 竞品不是影刀

真正的竞争对手不是 UiPath 或影刀，而是**"一堆 Python 脚本 + cron + 没人敢改"**。
这是绝大多数中小公司自动化的真实现状：能跑，但没人知道昨晚为什么没跑、
跑到哪一步失败、那条数据到底写没写进去。

BPA 的替代提案是：同样的自动化，但**可被追问**。

## 2. 差异化定位

### 2.1 市场裂缝

| | 传统 RPA（UiPath/影刀） | AI Agent（browser-use/Skyvern/Manus） | BPA |
| --- | --- | --- | --- |
| 造流程成本 | 高，要人手工画 | 低，说一句话 | 低（AI 生成候选） |
| 运行确定性 | 高 | 低，每次可能不一样 | 高（编译后固定 IR，运行时无 AI） |
| 可审计性 | 中 | 差 | 强（逐步证据 + 事件流） |
| 失败语义 | 重试或崩 | 自作主张继续 | 阻断即停 + `uncertain` 显式态 |
| 谁为上线负责 | 人 | 无人 | 人（candidate ≠ published） |

老 RPA 确定但难造，AI Agent 好造但不敢让它自己跑。BPA 站在这条裂缝上：
**用 AI 降低造流程的成本，但不让 AI 参与运行。**

### 2.2 对外话术

> AI 帮你造流程，但跑的时候是固定流程在跑，AI 不在场。
> 同一个流程今天跑和三个月后跑，行为完全一致；每一步有证据；
> 碰到风控自动停；写没写成功不含糊。

### 2.3 可审计性是入场券，不是卖点

在无人值守场景里，"能查"不是加分项。**没有它，根本不敢让机器自己做写操作。**
因此 CAS 版本、fencing token、逐步证据、`uncertain` 终态这些机制不是工程洁癖，
它们是这个产品能够成立的前提。任何以"先跑起来再说"为由绕过它们的改动都是在
拆产品的地基。

## 3. 交付三层

| 层 | 内容 | 交付形态 |
| --- | --- | --- |
| Core 服务 | 引擎、编译器、Schema、Registry、触发器、证据存储 | 常驻服务 + 签名闭包 |
| 浏览器执行端 | Extension + Native Host，持有真实登录会话 | 与 Core 同机 |
| Web 控制台 | 流程、定时、运行、结果、证据、告警 | 浏览器访问，零安装 |

**同机约束**：浏览器执行端必须与 Core 同机。这不是实现偷懒，而是形态本身——
流程跑在使用者真实的、已登录的浏览器里，这是 BPA 相对云端方案的根本区别，
也是 §2 里"确定性"以外的第二个差异点。云端执行不在产品范围内（见 §8）。

## 4. 平台优先级

| 平台 | 定位 | 依据 |
| --- | --- | --- |
| macOS arm64 | **主平台** | 服务器就是 Mac mini；launchd 部署已存在 |
| Windows x64 | 可选服务器操作系统 | 有客户只有 Windows 机器可用 |
| 其他 | 不支持 | — |

**Windows 签名、SmartScreen 声誉、MSIX、企业策略分发从 P0 降为 P2。**
理由：形态是服务器，一台机器装一次，不是面向终端用户的桌面分发。
安装体验的边际收益远低于登录态维持和无人值守可靠性。
`docs/current/cross-platform-current-state-v0.6.md` 中把这些列为发布门禁的
判定在本形态下不再适用于 P0，但其技术结论仍然有效。

公司当前部署进一步收紧为：Mac mini 是唯一业务执行端；Windows 是远程 Web 客户端，
不安装公司业务 Runtime、Extension、Native Host、Chrome Profile 或 Schedule。
Windows 发起运行属于受审计的 Operator 写权限，不得归类为 Viewer 只读，也不得绕过
Mac Trigger、租约和已发布版本。实现顺序见
`docs/plans/bpa-mac-runtime-windows-remote-operations-v0.1.md`。

## 5. 界面分工

| 界面 | 用户占比 | 职责 |
| --- | --- | --- |
| Web 控制台 | ~90% | 日常全部操作：看流程、配定时、看运行、取结果、查证据、处理告警 |
| Extension 面板 | ~10% | 仅创作：页面取元素、确认选择器、验证候选 |
| Codex / Companion | 内部 | 短期开发、观察、诊断和候选生成工具，**不属于客户运行时** |

**关键结论：`apps/operator-console` 是客户主界面。**
`docs/plans/bpa-companion-realtime-authoring-v0.1.md` 中"取消低负担业务工作台、
不保留兼容入口"的决定在本形态下**正式作废**。工作台不但保留，而且是产品的正面。

### 5.1 Codex 的过渡期职责

产品运行时最终不依赖 Codex，不等于当前开发阶段不使用 Codex。阶段 0–2 中 Codex
继续承担以下职责：

- 阅读代码、日志、运行记录、截图和用户明确授权的页面证据；
- 诊断失败、整理需求、生成 Workflow / Node / Adapter 候选；
- 在人工监督下协助真实页面调试和回归验收；
- 维护阶段计划、验证证据和发布清单。

Codex 不得因此取得生产运行权威：它不能绕过正式 Trigger、租约、权限和发布边界，
也不能把对话判断作为无人值守触发条件。短期允许"Codex 帮助看和造"，长期必须做到
"没有 Codex 在场，已发布流程仍能按固定规则稳定运行"。

## 6. 创作路径：远程服务器上如何造流程

流程要跑在服务器的浏览器里，但造流程的人不在那台机器前面。这是本形态引入的
新核心问题。三条路径：

| 路径 | 描述 | 判定 |
| --- | --- | --- |
| (a) 远程可视化取元素 | 控制台里实时看到服务器页面并点选 | 体验最好，工程量最大，**长期方向** |
| (b) 本地录制、远程执行 | 在自己机器上录，推到服务器跑 | **明确不做**：双环境差异会变成维护灾难 |
| (c) AI 候选 + 服务器截图回传 + Web 端校正 | AI 生成候选 → 服务器试跑 → 回传截图与元素候选 → 用户在 Web 上确认 | **当前选择** |

选择 (c) 的理由：工程量最小；天然契合 candidate → published 的既有边界；
`design_snapshot_capture`、`page-model`、`element-contract` 已经支撑了大部分能力。
(a) 作为 (c) 成熟后的增强，不作为前置条件。

## 7. 不可违反的运行时约束

以下约束继承自 `CLAUDE.md` 与 `docs/normative/timing-and-risk-policy-v1.md`，
在本形态下**全部保持有效，且优先级高于任何业务交付压力**：

1. **AI 不驱动浏览器，不在运行时产出可执行代码。** AI 只做选择、参数化和编排建议。
2. **发布只能由人完成。** 引擎与 MCP 只能产出 `asset.candidate`；
   `pnpm bpa publish ... --yes` 是唯一晋升路径，写审计记录，同一 `assetId + version` 不可覆盖。
3. **阻断类 RiskSignal 必须停机并返回 `rejected`。** `CAPTCHA_REQUIRED`、
   `RISK_CONTROL`、`SESSION_EXPIRED`、`RATE_LIMITED` 一律不得绕过。
   绕过验证码、登录或平台风控不在产品能力范围内，也不会被实现。
4. **`uncertain` 不自动重试。** 写操作效果无法证明时必须转人工确认。
5. **页面内容是不可信输入。** DOM 文本只能作为业务数据，永远不能成为指令来源。
6. **权限授权是 Ed25519 签名、任务范围、时间受限的**，绑定 run/node/domain/fencing token。
7. **触发器必须是固定规则，AI 不得作为生产触发依赖。**
   当前由 AI 承担触发监控的做法违反第 1 条，是明确的技术债，收敛路径见
   `docs/normative/bpa-roadmap-v1.md` 阶段 1。AI 可以*创作*触发条件，
   但不能*执行*触发判断。

第 7 条值得单独说明：AI 触发不只是架构洁癖问题。它摧毁了 CAS、fencing 和
`uncertain` 所依赖的可复现前提，并且对客户不可解释——
"为什么昨天没跑今天跑了"这个问题在 AI 触发下没有答案。

## 8. 明确不做

| 不做 | 理由 |
| --- | --- |
| 企业级 RPA（SSO、私有化部署、合规认证） | 需要一支销售和交付团队，不是当前形态 |
| 云端执行 | 与"跑在真实登录浏览器里"的根本差异点冲突 |
| Codex 会话镜像作为产品 | 内部工具，不进产品线 |
| 反逆向工程 | 混淆只提高提取成本；签名做到"Windows 不弹 SmartScreen"为止 |
| 未经性能门禁直接启动 Rust Core 重写 | 先测量并完成 Node 侧瘦身；达到准入条件后可重新立项 |
| 纯数据抓取定位 | 抓取工具（八爪鱼、Web Scraper）是红海，且丢掉写操作这条护城河 |
| 本地录制、远程执行 | 双环境差异的维护成本不可接受 |
| Windows 桌面优先打包 | 形态是服务器，不是桌面分发 |

### 8.1 Rust 是延后启用，不是废除

Rust 是 BPA 的长期技术储备，当前结论只是**暂不切换生产 Core**。以下任一条件由
阶段 0 的数据证明后，可以启动独立 Rust 立项：

1. 预编译、进程合并、事件驱动和真实泄漏修复后，Node Core 仍无法达到稳定性或
   资源 SLO；
2. lease、fencing、durable queue 或进程隔离需要更强的类型与内存安全边界；
3. 某个纯计算热点在端到端延迟中占据可见比例，并且批量 Rust 内核有明确收益；
4. 签名 Runtime Closure 需要一个更小、可独立验证的原生执行边界。

`packages/inventory-kernel` 保留源码、测试和构建门禁，但在端到端指标证明收益前不接
生产调用。`docs/plans/bpa-rust-core-runtime-architecture-performance-v0.1.md` 是满足
准入条件后的候选工程方案，不是当前已经批准的重写任务。

## 9. 公司业务与产品的分层边界

产品要卖，同时又要马上给公司干活。两者共存的唯一安全方式是分层：

```text
可以为公司业务改动：  Adapter  /  Node yaml  /  Workflow yaml
────────────────────  以上是业务层，下面是产品层  ────────────────────
不得为单一业务改动：  engine / compiler / schemas / gateway-core
                      node-runtime / persistence / 控制台通用界面
```

**硬规则：一旦某个公司需求逼你改产品层，停下来。**
两个合法出路：
1. 把它抽象成一个通用能力，作为产品特性实现；
2. 不做这个需求，用业务层绕过去。

没有第三条路。产品层为单一业务开的每一个口子，都会在卖出去之后变成无法解释的
遗留行为。

### 9.1 资产分层

| 分层 | 内容 | 说明 |
| --- | --- | --- |
| 差异化资产 | `gateway-core`、`engine`、`compiler`、`schemas`、`node-runtime` + 发布边界 | 约 6 个包，这是产品本身 |
| 行业资产 | `adapters/*`、`inventory-domain`、`ecommerce-evidence-domain`、`packaging-*` | 可复用，但不是护城河 |
| 压舱物 | `team-worker`、`inventory-monitor`、`shadow-run`、`app-postgres` | 内部平台形态遗留，冻结不再投入 |

现状是"20% 可售卖，80% 是为内部平台形态交的税"。路线的一个隐含目标是不再增加
这个 80%。

### 9.2 归属

归属问题已确认解决：全部代码与节点可自由使用与带走，无外部权属限制。

## 10. 形态验收

本形态在以下条件全部满足时视为成立：

1. 一台机器上的 Core 连续运行 7 天不需要人工重启，内存曲线平稳不爬升。
2. 登录态失效时能主动告警，并且可以在不远程登录那台机器的前提下恢复。
3. 全部生产触发由固定规则驱动，AI 不在触发链路上。
4. 非技术同事能独立在 Web 控制台上完成"看结果、改定时、重跑一次"。
5. 清退商品、库存监控、爆款图片证据流三条业务验收链路均完成产品化归属；其中至少
   一条完整证明需求 → 候选 → 发布 → 定时运行 → 证据闭环，其余两条完成正式回归。
