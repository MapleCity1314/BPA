# BPA 路线与阶段 v1

> 文档类别：阶段划分、优先级与验收判定的正式约定。
> 记录时间：2026-08-06。
> 权威等级：normative。形态依据见 `docs/normative/bpa-product-form-v1.md`。
> 本文件规定"先做什么、后做什么、什么时候算做完"。

## 0. 排序原则

阶段顺序不是按工程难度排的，是按**"不做它，下一步就没意义"**排的：

1. 服务器跑不稳 → 谈不上无人值守。
2. 登录态会掉且掉了没人知道 → 谈不上无人值守。
3. 无人值守不成立 → 好用的创作界面没有价值，造出来的流程也守不住。
4. 创作不好用 → 只有开发者能用，卖不出去。
5. 以上都成立 → 才轮到通用能力和对外交付。

**任何把后面阶段的工作提到前面做的提议，都需要先说明它如何不违反这条依赖链。**

同时存在一条并行约束：公司业务现在就在这台机器上跑，不能停。因此每个阶段都
必须以"业务不中断"为前提设计，不允许出现"先拆掉再重建"的窗口期。

## 阶段 0：稳住上阵

**目标：这台 Mac mini 上的 Core 能连续跑，不需要人盯着重启。**

### 0.1 先收敛在途改动

当前分支 `codex/protocol-v2-decoupled-runtime` 相对 main 有 315 个文件、
+34950/−1417；工作区另有 75 个未提交文件。

在这个状态上叠加任何新设计都是不安全的：新 Schema 会被冻结在一个尚未验证的
协议迁移之上。

- 合并或明确放弃 protocol-v2 分支。
- 清空未提交改动。
- `pnpm check` 全绿作为进入阶段 1 的硬门禁。

### 0.2 内存问题必须先测量再动手

服务器上 Node 占用巨大是事实，但目前**没有测量数据**，只有结构性推断。
在测出曲线之前不允许做任何性能改造。

三个内存桶必须分开测，因为解法完全不同：

| 桶 | 测法 | 含义 |
| --- | --- | --- |
| Node 进程 | 按 pid 记录 RSS，至少 24 小时 | 起步就高 = 架构问题；持续爬 = 真泄漏 |
| 浏览器 | 单独统计 Chrome 进程树 | 按需启动是否真的退干净 |
| SQLite | page cache 配置与实际占用 | 通常是可配置项，不是泄漏 |

**判据：曲线平 = 起步高，属于架构成本；曲线爬 = 真泄漏，在 7×24 服务器上是致命的。**

- 起步高的结构性原因（已定位，未验证）：`tsx` 源码运行覆盖 44 个包；
  六个独立 Node 进程各带一份 V8 基线。
- 爬升的可疑点（已定位，未验证）：`apps/local-core/src/browser-gateway.ts`
  中的常驻 Set/Map 结构、事件累积、SQLite page cache。

### 0.3 优化顺序（不得跳步）

1. 测量（0.2）。
2. 去 tsx：生产路径改为预编译产物运行。
3. 合并进程：六个 Node 进程能合几个合几个。
4. 事件驱动 + 空闲退避：`apps/local-core/src/main.ts` 的 500ms gateway tick
   在空闲时是纯自旋，改为事件驱动加退避。
5. 修真实泄漏（如果 0.2 证明存在）。
6. **评估 Rust 准入门禁，满足后单独立项。**
   `@bpa/inventory-kernel` 已有的 5.27 倍加速（约 1400ms → 266ms）在
   3–10 秒的页面等待面前目前不可见，但这只证明它不应优先接入库存生产，不代表
   Rust 被废除。准入条件见产品形态定义 §8.1。

### 0.4 待查项

以下两个问题的答案会改变后续设计，必须在阶段 0 查清：

1. **浏览器 profile：已确认。** 2026-08-06 只读进程核验确认库存 Chrome 使用固定的
   `chrome-inventory-profile`，登录态并非因每次创建全新 profile 而丢失。当前浏览器
   由 launchd `KeepAlive` 常驻，与目标按需形态存在差距；是否改动要结合 24 小时
   Chrome 资源曲线和登录稳定性决定。
2. **Node 内存曲线是平还是爬？** 采样已启动，结论待满 24 小时后写入。

### 0.5 顺带

- `CLAUDE.md` 已过时（描述约 10 个包 / 1 个 adapter；实际 44 包 / 10 apps / 2 adapters）。
  在阶段 0 内更新，因为它是所有 AI 协作的入口文档，过时会持续放大成本。

### 0.6 Codex 过渡期

阶段 0–2 继续使用 Codex 阅读代码、日志、截图、运行记录和授权页面，协助诊断、开发
与候选生成。每项结论必须落到可复查的代码、测试、运行记录或证据资产中。Codex
可以参与人工监督的调试，但不能成为正式调度器、生产租约持有者或不确定写入的自动
重试者。随着阶段 1 的固定 Trigger 覆盖率上升，Codex 在生产触发链路中的占比必须
单调下降到零。

### 阶段 0 验收

- `pnpm check` 全绿，工作区干净。
- 三个内存桶各有一条 ≥24 小时的曲线记录。
- Core 连续运行 7 天无需人工重启，RSS 不呈单调爬升。
- 浏览器 profile、常驻策略和 Node 内存曲线有明确书面结论。

## 阶段 1：无人值守成立

**目标：机器自己跑，出事了人立刻知道，并且能在不远程登录服务器的前提下恢复。**

### 1.1 登录态维持与恢复（最高优先级）

这是无人值守形态的第一障碍，**优先级高于创作体验，也高于录制器**。

现状：`SESSION_EXPIRED` 已经能正确阻断并返回 `rejected`。这是对的，但产品在
"停下来之后怎么办"这一段是空白。

必须补齐的三件事：

1. **延长有效期**：持久化 profile + 周期性轻量保活，减少验证码触发频率。
   前提是 0.4 的第 1 项已查清。
2. **失效即告警**：登录态失效时主动推送，不依赖人去翻控制台。
3. **远程恢复入口**：用户在手机上就能完成重新认证，不需要 SSH 或坐到那台机器前。

目标是把体验从"随时可能挂、要你去查"变成"挂了立刻通知、手机上点一下就恢复"。

**边界重申**：绕过验证码、登录或平台风控不在范围内，也不会实现。
本节做的全部是"降低人工介入成本"，不是"消除人工介入"。

### 1.2 失败告警

任何 run 进入 `rejected` 或 `uncertain` 必须推送。
`uncertain` 尤其重要——它意味着一个写操作的效果无法证明，且按规则不允许自动
重试，因此它**必然**需要人来看。没有推送，`uncertain` 就等于静默丢单。

### 1.3 定时与触发的 Web 界面

`apps/local-core/src/control.ts` 已有 `trigger.{put,list,runs,enable,fire}`，
底座存在，缺的是界面。

### 1.4 AI 触发 → 固定规则（技术债，明确收敛路径）

**这是当前唯一一处正在运行的、违反产品核心原则的实现。**

现状：触发监控由 AI 承担。这直接违反"AI 不参与运行"，并且摧毁了 CAS、fencing
和 `uncertain` 所依赖的可复现前提。对客户也不可解释——
"为什么昨天没跑今天跑了"在 AI 触发下没有答案。

**不立即拔掉。** 公司业务正跑在上面，直接停掉不现实。收敛按下列路径进行：

- 设计不需要重新发明：`docs/plans/deterministic-workflow-triggering-v0.1.md`
  已经定义了 TriggerSpec 和 Manual / Schedule / Dataset / Domain Event 四类触发，
  且 Manual / Schedule / Dataset 的最小平台内核**已经实现**。
  本阶段的工作是把现有 AI 触发逐条映射到这套既有设计上，而不是另起一套。
- 对于确实需要判断的场景，正确形状是：
  **固定规则触发 → 只读流程取数 → 进人工复核队列 → 人确认后才写。**
  AI 可以*创作*触发条件，不能*执行*触发判断。
- 每迁移一条，在控制台上可见其触发类型，直到 AI 从触发链路上完全消失。

### 1.5 合并两个控制台

现状是一个应用对一个控制台。

**这件事必须在阶段 1 做，理由是时间窗口：现在只有一名使用者，合并的迁移成本
接近于零；一旦有非技术同事开始依赖某个控制台，合并就变成不可能。**

### 1.6 远程查看运行记录与证据

Web 控制台上能看到每一次运行的步骤、结果、证据链。这是 §2.3 里"可审计性是
入场券"的产品体现——机制已经在引擎里了，缺的是把它呈现出来。

### 阶段 1 验收

- 登录态失效可远程恢复，全程不需要登录那台机器。
- 失败与 `uncertain` 100% 触发推送。
- 定时配置、运行记录、证据在 Web 控制台上可见可改。
- 只剩一个控制台。
- 生产触发中 AI 的占比有明确的、单调下降的数字。

## 阶段 2：造流程易用

**目标：非技术同事能自己造出一条能用的流程。**

采用形态定义 §6 的路径 (c)：

```text
AI 生成候选 → 服务器试跑 → 回传截图 + 元素候选 → 用户在 Web 上确认 → 候选 → 人发布
```

已有支撑：`design_snapshot_capture`、`design_mode_start/stop`、
`page-model`、`element-contract`、`candidate_bundle_*`。
缺的主要是 Web 端的校正界面和回传链路。

**candidate → published 的人工发布边界在本阶段不得放宽。**
路径 (c) 之所以被选中，恰恰是因为它天然落在这条既有边界上。

### 阶段 2 验收

**一个非技术同事，在没有开发者协助的情况下，独立造出一条能跑的真实流程。**
这是唯一验收标准，不接受"开发者演示一遍"作为替代。

## 阶段 3：通用能力

**目标：不写 Adapter 也能覆盖大部分需求。**

- 通用副作用节点最小集：受策略约束的 HTTP Request、原子 File Write、
  结构化 JSON Transform。
  `nodes/core/` 现有 56 个节点中没有这三个。
  约束继承自 Companion v0.1 §5：HTTP POST 不是 Adapter 的替代品（平台特有认证、
  签名、限流、分页、错误语义仍属 Adapter）；File Write 必须限制根目录、
  临时文件后原子替换，且对不确定结果不自动重试。
- Excel / CSV 导出。这是取数类需求的实际终点，缺了它流程等于没跑完。
- 元素自愈：选择器失效时的降级与候选重选。
- **Adapter 降级为可选增强，不再是新平台接入的必经之路。**

## 阶段 4：可交付给外部客户

- 单机安装脚本（一台机器装一次，不是终端分发）。
- 授权 / license。
- 多用户与权限。

此阶段之前，产品只服务于自己公司。**不允许为了"将来能卖"而提前把阶段 4 的
复杂度引入前面任何阶段。**

## 暂缓与冻结清单

以下项目不能抢占当前阶段。"暂缓"表示准入证据成立后可以启动；"冻结"表示除非有
新的产品级理由，否则不再投入：

| 项目 | 状态 | 理由 |
| --- | --- | --- |
| `packages/inventory-kernel` 与 Rust Core 方案 | **暂缓** | 保留实现和门禁；完成阶段 0 测量并达到产品形态定义 §8.1 后再立项 |
| `apps/team-worker` | **冻结** | 内部平台形态遗留 |
| `apps/inventory-monitor` | **冻结扩展** | 现有生产继续维护；业务能力迁入正式 Node / Workflow，不再扩大 App 特例 |
| `shadow-run`、`app-postgres` | **冻结** | 内部平台形态遗留 |
| Windows 签名 / SmartScreen / MSIX | **暂缓到 P2** | 形态是服务器，不是终端桌面分发 |
| Codex Companion 实时会话通道 | **内部可用、产品冻结** | 短期开发观察可用，不成为客户产品或生产依赖 |

## 三条最终业务验收链路

三条链路用于证明 BPA 核心产品，而不是把业务特例写入 Core：

| 链路 | 当前角色 | 产品化目标 | 最终证据 |
| --- | --- | --- | --- |
| 清退商品工作流 | 只读、多店浏览器流程 | 证明平台 Adapter、foreach、恢复、结果聚合和告警 | 登录态真实页面 E2E、完整扫描证据、失败与恢复回归 |
| 库存监控工作流 | 当前公司生产压舱链路 | 证明固定 Trigger、lease/fencing、部分成功、数据新鲜度和无人值守 | 连续生产窗口、13 店覆盖、订单/库存/预测/风险分离证据 |
| 爆款图片证据流 | 证据领域与回放候选 | 证明页面证据、图片资产、来源授权、内容寻址和可复用参考包 | 原图、来源、指标、角色说明、回放及 Web 控制台可见性 |

实施顺序仍服从阶段门禁：阶段 0 保持库存生产并建立基线；阶段 1 完成库存无人值守；
阶段 2 用清退商品验证非技术创作与真实页面校正；阶段 3 补齐爆款图片所需通用取数、
文件和导出能力；阶段 4 前对三条链路执行统一发布闭包回归。

## 阶段间硬约束

1. **不得跳阶段。** 依赖链见 §0。
2. **公司业务不中断。** 不允许"先拆掉再重建"的窗口期。
3. **分层边界不可突破。** 公司需求只能改 Adapter / Node yaml / Workflow yaml；
   一旦逼你改 engine / compiler / schemas / gateway-core / node-runtime /
   persistence / 控制台通用界面，停下来，按形态定义 §9 的两条出路处理。
4. **运行时安全约束在任何阶段都不让位于交付压力。** 见形态定义 §7。
