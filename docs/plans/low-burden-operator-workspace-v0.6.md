# BPA 0.6：低负担业务工作台

## 状态

- 权威等级：迭代计划
- 实现状态：部分实现
- 产品原则：减负优先、治理下沉、异常聚合、结果先行
- 不改变的边界：权限、Evidence、Session、Fencing、审计、人工发布与
  R2+ 确认继续生效

## 1. 核心目标

BPA 0.6 不以继续增加平台概念为目标，而是解决“平台很强，但用户很累”。
普通业务用户只需要理解目标、必要动作和结果：

```text
用户表达目标
→ BPA 自动检查环境和选择能力
→ 必要时请求一次页面授权
→ 自动执行、恢复和收集证据
→ 只在真正需要时集中询问
→ 用户直接查看业务结果
```

治理规则继续存在于 Core 与协议层，不能通过简化界面绕过。

## 2. 用户角色

### 运营模式

默认只显示首页、任务、结果和自动化。CLI、Session ID、Schema、摘要和协议
不进入常规路径。

### 创作模式

业务负责人描述目标、授权页面学习、提供必要页面状态，并审核自动化草稿。
Authoring Session、Profile 与 revision 由系统管理。

### 开发者模式

隐藏在高级设置中，保留 Runtime、协议、Browser Session、Evidence 摘要、
Node Execution、事件和诊断日志。

## 3. 业务工作台

首页只回答：

1. 现在可以做什么。
2. 哪些任务正在运行。
3. 有什么需要处理。
4. 最近得到了什么结果。

健康状态保持安静；只有影响任务时才显示“BPA 需要处理”。任务启动采用
“选择事情 → 确认范围 → 必要时选择页面 → 开始”的向导，Workflow、Dataset
Profile、Browser Session、权限、风险、恢复和 Evidence 策略由系统预检。

任务详情按照进度、用户动作、业务结果、证据来源、技术事件的顺序展示。
结果中心优先展示检查数量、真实问题、重要程度、不可用数据和导出入口，
Evidence 血缘按需展开。

## 4. 页面授权与环境修复

常规路径最终替换复制粘贴绑定 JSON：

```text
授权 BPA 使用当前页面
```

Extension 在用户手势下提交精确 Tab、Origin、PageEpoch、Browser Session、
Chrome Profile 与短期授权。15 分钟 TTL、Origin 限制与审计不变。

工作台启动时自动完成 Core、Extension、Chrome Session、版本和 Native Host
检查。可恢复问题自动处理，只有无法自动处理时才显示业务化动作，例如重新加载
扩展、登录来源平台或打开目标页面。

## 5. 人工关注预算

`AttentionItem` 使用以下等级：

- `information`：仅通知。
- `review`：可以稍后批量审核。
- `action`：需要完成外部动作。
- `approval`：长期影响或风险确认。
- `blocking`：当前任务无法继续。

每项必须说明介入原因、具体动作、是否阻塞、能否批量、已尝试的恢复，以及
完成后是否自动继续。相似歧义聚合；同一阶段最多一次集中确认；可恢复错误不打扰
用户；登录失效只暂停对应资源；R2+、正式发布和长期绑定保持单独确认。

## 6. AI 创作

创作首页只要求描述业务目标。Codex 在后台整理 ScenarioSpec、搜索 Catalog、
登记 Capability Gap、选择页面、生成候选并汇总风险。用户路径为：

```text
描述目标
→ 授权页面
→ 展示必要状态
→ BPA 自动学习
→ 审核自动化草稿
```

审核优先说明自动化行为、访问范围、人工点、失败语义和新增能力。源码、摘要和
契约测试放入高级视图，Candidate 仍不能自动执行、写入源码或发布。

## 7. 视觉与交互

Operator Design System 使用冷白、纯黑和一个品牌强调色；增大中文字号和行高，
减少小卡片、边框和标签；一屏一个主要动作；异常才获得视觉重量；技术信息渐进
披露；支持明暗主题、键盘、Reduced Motion，以及 512px、768px、1440px。

## 8. 架构

新增纯领域模块：

```text
packages/attention-core
packages/interaction-policy
packages/operator-read-model
```

- `attention-core`：人工关注项、优先级和批量聚合。
- `interaction-policy`：决定静默恢复、延后、聚合或打断。
- `operator-read-model`：把 Engine、Assistance、Browser 与 Evidence 投影为
  业务视图。

Engine 不包含 UI 逻辑，Console 不自行推断状态，Console Host 不直连 SQLite，
Gateway 不承担业务编排，所有操作继续通过 Control、CAS 和 Audit。

## 9. 实施波次

1. 记录当前操作路径、内部概念与人工介入预算。
2. 实现 AttentionItem、异常聚合和业务任务投影。
3. 自动 Doctor、多 Profile 发现、一键页面授权与授权恢复。
4. 重构首页、任务、结果、自动化、任务详情和结果中心。
5. 自然语言创作向导、自动会话/revision 管理和候选审核。
6. 使用重点项检查与蝉妈妈指标读取做真实业务验收。

Windows x64 与 macOS arm64 必须共用上述领域和前端代码。平台差异仅允许存在于
路径、IPC、服务管理、Native Host 注册和发布闭包。

## 10. 验收

- 已发布只读任务健康时零人工介入。
- 运营人员不需要 CLI 或内部标识。
- 页面授权不再复制 JSON。
- 登录恢复最多一次明确操作。
- 相似歧义只形成一次批量确认。
- 已有节点创作最多两次业务确认。
- 新页面只读创作只需一次授权、必要页面切换和最终审核。
- 首页 5 秒内能理解可用性、待办与最近结果。
- 技术信息默认折叠但完整可追溯。
- 安全、审计、恢复和人工发布边界不弱化。

成功标准不是“页面更好看”，而是用户理解、操作和等待更少，同时对结果更有
信心。
