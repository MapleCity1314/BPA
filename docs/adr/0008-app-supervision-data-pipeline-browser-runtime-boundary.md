# ADR 0008：BPA App 的监督、数据链路与浏览器运行时边界

- Status: accepted
- Date: 2026-08-05
- Implementation: partial

## Context

抖店库存应用已经证明数据库写入、预测和风险计算可以独立产出，但生产运行仍呈现出“持续读取订单、采集不稳定、部分数据已经入库却被描述为无数据”的现象。

本决策依据以下复盘：

- [BPA 工作台与页面绑定复盘 v0.1](../research/BPA工作台与页面绑定复盘-v0.1.md)
- [抖店库存浏览器工作流稳定性复盘 v0.1](../research/抖店库存浏览器工作流稳定性复盘-v0.1.md)

详细问题登记和实施设计已拆分为：

- [抖店库存生产链路问题与决策记录 v0.1](../research/抖店库存生产链路问题与决策记录-v0.1.md)
- [BPA 确定性触发与自动运行设计 v0.1](../plans/deterministic-workflow-triggering-v0.1.md)
- [BPA App 解耦设计准则 v0.1](../plans/bpa-app-decoupling-guidelines-v0.1.md)

本 ADR 只保留跨文档的正式架构决策；生产事实、平台能力计划和 App 开发检查清单分别由上述文档维护。

并补充 2026-08-05 的生产检查事实：

- Codex 自动任务仍指向已经停用的 `com.bpa.inventory-scheduler`，而生产实际使用 `com.bpa.inventory-multishop-recovery`。
- 多店铺恢复脚本对每家店无条件执行近期订单读取，并在失败时重复执行，订单步骤因而长期占据可见运行时间。
- 高频错误集中在 `BROWSER_AUTH_REQUIRED`、`INVENTORY_SHOP_SWITCH_ENTRY_NOT_READY` 和 `INVENTORY_PRODUCT_PAGE_NOT_READY`，而库存快照、预测和风险事实仍能产生。
- launchd 退出状态、应用状态文件和数据库运行终态可能不一致，单独使用任一状态都可能造成误判或重复触发。
- 渠道冷启动产生的 `unknown` 会向上污染商品级风险，数据不足与确定性库存风险没有彻底分开。

这些事实说明，问题不应被概括为“BPA 整体不可用”或“数据库没有处理数据”。主要缺口位于控制面重复、领域步骤耦合、浏览器资源就绪语义和结果表达。

## Decision

### 1. 每个 BPA App 只能有一个生产调度控制面

生产调度由 App 自己的确定性调度器和操作系统守护进程负责。Codex 自动任务只承担监督和有条件的故障兜底，不成为第二个业务调度器。

对库存应用：

- `com.bpa.inventory-multishop-recovery` 是当前唯一允许被监督任务触发的多店铺恢复入口。
- 已停用的 `com.bpa.inventory-scheduler` 和 `com.bpa.inventory-recovery` 不得再被自动任务检查或启动。
- Codex 不直接调用 `refresh-missing.ts`、`refresh-recent.ts`、`refresh-risk.ts` 等内部脚本。
- 触发前必须同时确认没有运行进程、没有有效 PostgreSQL 租约，并且上一轮不在合理执行窗口内。
- Codex 自动任务不修改业务事实、不发布工作流、不修改平台库存，也不发送外部通知。

Codex 自动任务适合处理需要推理的监督职责：解释跨组件状态、聚合中文诊断、识别需要人工介入的登录或页面问题。固定频率、租约、重试、恢复和数据处理必须留在确定性应用代码中。

### 2. 调度事实采用组合判定，派生状态不得反向控制生产

运行中的事实由以下信号组合判定：

1. launchd 进程或受管子进程状态。
2. PostgreSQL 有效租约和 fencing token。
3. 数据库中的最新运行记录及其终态。

状态 JSON、日志摘要和前端标签属于派生视图。派生视图与上述事实不一致时，系统应报告“运行状态不一致”，不得据此叠加启动新任务。

每轮必须产生 `complete`、`partial`、`blocked` 或 `degraded` 之一，并包含发现、尝试、持久化、失败和跳过数量。只要存在已验证并持久化的部分结果，就不得把该轮表达为“无数据”。

### 3. 数据采集、事实发布、计算和展示解耦

库存 App 拆分为四类独立职责：

```text
浏览器采集器 / 数据库同步器
→ 发布版本化事实
→ 预测与风险计算器
→ 领域 API 与业务面板
```

具体规则：

- 库存浏览器采集只负责库存事实，不负责等待订单、拟合模型或发送提醒。
- 近期订单读取按店铺新鲜度独立调度；有效期内直接复用现有事实，不得每轮每店无条件重读。
- 历史订单从 MySQL 等稳定数据源独立同步，不依赖浏览器库存任务成功。
- 预测和风险计算消费固定数据集版本，可以由新事实事件触发，也可以独立补算。
- 面板只查询领域 API 和已发布事实，不直接控制浏览器工作流。
- 外部通知消费已确认的风险事件；采集、计算和通知任一层失败不得破坏其他层已提交的数据。

库存与近期订单的生产新鲜度当前统一为 120 分钟，历史订单完整日门槛为 36 小时。新鲜度是是否需要刷新某类事实的依据，不是重新执行整条链路的依据。

### 4. App 数据库与 BPA Core 运行状态分离

BPA Core 保留自身运行和协议状态的持久化。每个生产 App 使用自己的领域数据库、迁移、租约、事实和审计表。

BPA 工作流通过固定、版本化的服务节点或受限 Unix Socket 使用 App 能力，不获得数据库凭证、自由 SQL、任意文件路径或任意 HTTP 权限。App 数据库事实可以被多个工作流组合复用，但工作流不得成为领域数据库的隐式迁移工具。

### 5. Page Binding、控制权、节点权限和外部效果确认分离

结合两篇复盘，BPA App 的浏览器设计必须明确四个不同边界：

| 边界 | 负责回答 | 负责层 |
| --- | --- | --- |
| Page Binding | 使用哪个浏览器、店铺和页面 | Extension + Core |
| Control Lease | 当前谁可以操作该页面 | Core + 跨 RPA 协调 |
| Capability | 节点被允许读取或修改什么 | Node + Adapter + Runtime |
| Effect Confirmation | 是否允许库存修改、发布或外部发送 | App + Interaction Policy |

长期 Page Binding 不应因一次页面刷新、SPA 路由变化或 Extension 短暂重连而失效。一次观察的 PageEpoch 可以变化，但不能代替长期资源身份。

### 6. 浏览器任务必须具有系统级开始—恢复—释放闭环

每个受管浏览器命令必须遵循：

```text
获取控制租约
→ 验证绑定、店铺、登录和页面角色
→ 执行金丝雀
→ 执行有限范围业务动作
→ 持久化结果或失败证据
→ 关闭自身抽屉和浮层
→ 恢复滚动、分页和基准页面
→ 只回收自身创建的标签页
→ 验证恢复
→ 释放控制租约
```

共享浏览器环境中，如果其他 RPA 不支持统一控制租约，生产部署必须使用独立 Profile、窗口或浏览器实例进行物理隔离。数据库租约不能代替浏览器控制租约。

### 7. 浏览器就绪判断必须抗瞬时状态

DOM 可见不等于 BPA 可以安全读取。开始业务节点前必须同时确认：

- 页面语义目标存在且在稳定窗口内没有变化。
- Extension 已绑定到预期 Browser Instance、Profile 和 Tab。
- 当前店铺身份与工作流范围一致。
- 登录状态连续稳定，而不是一次瞬时观察。
- 没有未知弹窗、验证码、风控或其他控制者。

短暂缺失绑定不得立即归类为真正的 `BROWSER_AUTH_REQUIRED`。运行时可以执行一次有界的重新观察或重新绑定；仍不满足时才阻断。不得通过整段订单工作流多次重跑来掩盖就绪契约缺失。

### 8. 部分成功和局部恢复是浏览器批处理的一等语义

单商品失败不得默认终止全部商品。每个商品应拥有可观察状态、局部超时、失败阶段和证据 ID，并在失败率达到明确熔断门槛时停止剩余批次。

已成功商品应立即持久化。调用方根据覆盖率、新鲜度和失败类型决定是否继续计算，不以工作流是否到达单一 `succeeded` 终态推断是否存在数据。

### 9. 数据质量与业务风险分开表达

- 渠道冷启动、映射置信度不足和快照覆盖不足属于数据质量状态。
- SKU 或商品是否会在预测窗口内耗尽属于业务风险。
- 某渠道为 `unknown` 不得自动把整个商品提升为开放库存风险。
- 只有决定商品风险所必需的库存、订单或身份事实本身不可信时，才阻断商品级确定性判断。
- 数据质量事件和库存风险事件使用不同的唯一键、生命周期、面板分组和通知策略。

### 10. BPA App 的业务入口与开发者入口分离

业务员工使用结果型领域面板，只看到需要处理、风险、数据新鲜度、运行状态和最近结果。Workflow、Node、Adapter、Browser Session、Dataset ID、Evidence Digest 等实现术语默认隐藏。

Operator Console 作为开发者诊断入口，展示绑定、控制租约、执行时间线、数据集版本、诊断包和 Developer Capture。面向业务用户的 Design Mode 被一键 Page Binding 替代；复杂页面的开发通过 Developer Capture、脱敏夹具和离线回放完成。

## Rejected alternatives

### 让 Codex 自动任务成为主调度器

拒绝。Codex 适合监督和解释异常，不适合承担确定性频率、锁、fencing、幂等和长任务恢复。这样会形成第二控制面，并放大重复执行风险。

### 每轮依次执行订单、库存、预测和通知

拒绝。任何浏览器瞬时错误都会阻断后续步骤，也无法复用仍然新鲜的数据。

### 通过增加整轮重试解决浏览器不稳定

拒绝。整轮重试会增加页面漂移、标签页堆积和跨 RPA 冲突。恢复必须是有界、局部且带证据的。

### 用数据库租约代表浏览器独占

拒绝。外部 RPA 和人工操作不会读取 BPA 数据库租约，必须使用可共享的控制协议或物理隔离。

## Consequences

- App 将拥有更清晰的服务、事实、调度和业务展示边界，但需要增加独立任务状态和跨任务可观测性。
- 浏览器采集可以失败或降级，而不会抹掉已经提交的数据，也不会无条件阻断预测补算。
- Codex 自动任务的职责明显缩小，误触发概率降低；固定故障恢复仍需由应用代码实现。
- Page Binding 和浏览器运行时能力应成为 BPA 平台能力，避免每个业务 Adapter 重复实现。
- 业务面板更简洁，但开发者诊断控制台必须保留足够证据定位真实页面问题。

## Implementation status

截至 2026-08-05：

- 已完成：Codex 自动任务改为监督并安全触发 `com.bpa.inventory-multishop-recovery`，停止引用两个旧任务；采用 120 分钟新鲜度；禁止直接调用内部刷新脚本；增加状态不一致和部分成功判断。
- 已具备但待生产验收：PostgreSQL 租约、fencing token、逐商品持久化、多店铺配置、部分标签页生命周期管理。
- 尚未完成：订单按新鲜度跳过、采集器物理解耦、跨 RPA 控制租约、统一批次摘要、诊断包、商品级局部恢复、数据质量与库存风险分流。

## Acceptance criteria

- 生产环境只有一个组件负责周期调度，Codex 不直接执行领域脚本。
- 近期订单有效时，库存采集不会重复读取订单。
- 单个采集器失败不会撤销其他采集器已经发布的事实。
- 每轮都有可核对的终态和数量摘要，部分入库不显示为无数据。
- 绑定刷新或 Extension 短暂重连不会立刻被误判为登录失效。
- 其他 RPA 持有控制权时 BPA 明确等待、跳过或停止，不同时操作。
- 业务面板分别展示库存风险、数据质量和采集故障。
- 历史故障可以通过脱敏夹具和诊断包离线复现。
